#+title: Arp Speed: Chord
#+options: ^:nil -:nil

Included in community 1.38-rc1. The user liked
chd2's chord voicings and reports chd3 works far better after switching back
to ordinary arp. This is practical feedback, not exhaustive hardware coverage.
The main user guide now includes Chord under Arpeggiator. Humanize does not
apply to generated Chord; ordinary arp uses velocity/late onset only.

* Try it
:PROPERTIES:
:CUSTOM_ID: try-it
:END:
Enable Arp on a sequenced track. Select its Type, then turn Arp Speed past 1/1
to Chord. A step's gate-eligible positive-velocity Notes supply the input.
Start with one note and compare Up 1, Up 4 and Random 4, then try a few input
notes. Polyphonic MIDI/Bitwig is the clearest reference; mono CV cannot play a
chord. Existing poly CV allocation has its usual hardware voice limits.

This is a pragmatic range-based chord generator, not harmonic analysis.

* Revised musical rule (chd2)
:PROPERTIES:
:CUSTOM_ID: revised-musical-rule-chd2
:END:
Compaction is removed. For a single distinct melodic input pitch, fill a
four-note voicing according to the arp's octave-range number. In C major,
starting at C4:

| Range | Up / Up-Down / Order / Random / Up-Low | Down / Down-High |
|-------+----------------------------------------+------------------|
| 1     | C4 E4 G4 C5                            | C4 G3 E3 C3      |
| 2     | C4 G4 C5 G5                            | C4 G3 C3 G2      |
| 3     | C4 G4 C5 C6                            | C4 G3 C3 C2      |
| 4     | C4 C5 C6 C7                            | C4 C3 C2 C1      |

Third and fifth mean the third/fifth available scale notes counted upward from
the quantized starting note, using effective Hrm/root/scale and normal
transpose ordering. D in C major therefore gives D F A D, not D F# A D.
Downward voicings use those same pitch classes below the starting note, not a
negative third/fifth that would invent a different chord. Root Off retains
C-based scale processing and subsequent stored transpose.

Chromatic has no diatonic third/fifth, so use a major third/perfect fifth as
the simple fallback. Scales with fewer than five notes per octave use the
octave for a missing degree; duplicates are removed, so fewer than four notes
can result. Repeated identical input pitches count as one note. Drum tracks do
not receive this harmonic fill.

Repeat types have rhythmic ratios rather than octave ranges: they use the
range-1 fill. Single-note Random/Order/Up-Down use the upward voicing of their
range; this first rule does not randomly change its orientation per step.

With multiple distinct input pitches, run the selected existing arp program
from its start, collecting the first four distinct generated pitches without
octave folding. Sample at most 16 ordinary advances, each bounded by the
existing 100-instruction limit. This is not a complete-cycle enumeration; with
enough input notes, different ranges may still share the first four. Random
multi-note arps retain their existing randomness.

Send the group on the same sequencer tick, using the first eligible input
note's velocity. MIDI messages are serialized on the wire. Use one duration:
actual step interval times track Gate Time, minimum one tick. Input note
lengths/delays/ratchets and Arp Gate are ignored. A new chord releases the
previous chord before retriggering. Out-of-range pitches are omitted, not
wrapped. Normal output harmony/transpose still applies and can merge pitches.

* Scope and limitations
:PROPERTIES:
:CUSTOM_ID: scope-and-limitations
:END:
Chord is triggered by sequencer steps only. Live-only held keyboard input does
not free-run or generate chords in this first prototype. Empty or fully gated
steps produce no new chord; an existing chord can finish its gate tail. Local
Gli is ignored as on other arp input; persistent CCi34/35 still reaches
generated attacks, with the existing shared-output limitations. Chord mode is
not added to grid prediction or Inv Bias processing.

Stop/track cleanup, disabling arp, type changes and crossing into/out of Chord
release generated voices. Crossing the Chord boundary restarts the arp program
and rate phase, while retaining live keys and unexpired ordinary sequencer
inputs until their matching releases. Chord attacks do not replace their
velocity. Returning to a normal rate resumes those remaining inputs on the
next arp tick; notes played only as sequenced Chord attacks are not retained.
Ordinary rate-to-rate changes are unchanged. Random programs are not rewound.
Straight performance timing includes Chord as its endpoint after 1/1, with
next-bar switching; its menu shows Chord >bar pending. CCi/Remote CC26
intentionally keeps the original 17-rate scaling; it cannot select Chord. A
latched CCi speed retains precedence over the stored choice.

The additional stored Arp Speed index is 17; all old indices stay unchanged.
Track step index17 still means 1/3 bar, not Chord. Numeric song version1.38
marks the new capability; six-byte events and 20480-byte songs stay unchanged.
Back up before saving: older firmware cannot interpret the Chord speed.
Host JSON/upload tools support 1.38 as schema5/profile carbon-1.38-arp-chord,
which allows arp speed index 17; earlier profiles reject it. No implicit
profile edits or downgrade.

Tests exercise all37 built-in types with one through six notes, <=4 outputs,
single-note range voicings, scale degrees and deduplication, common gate time
and note cleanup, production step batching, speed/type/disable transitions, UI
label distinction, Straight endpoint and song save/reload. Existing suites
pass. Bounded work is not a measured worst-case interrupt budget: busy
six-track hardware timing still needs checking. This prototype adds no
full-song buffer.
